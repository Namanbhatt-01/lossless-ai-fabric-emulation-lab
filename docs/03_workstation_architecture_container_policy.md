# SECTION 7: M1 MacBook Air (8 GB RAM) Workstation Architecture & Container Resource Policy

This policy specifies the container runtime configuration, cgroups v2 limits, and memory budgeting parameters to maintain a 5 GB free memory headroom on macOS Apple Silicon.

---

| Workstation Layer | Selected Tool / Framework | Resource Allocation on 8-GB M1 | Configuration & Optimization Settings | Operational Role in Portfolio Workflow | Failure Mode Prevented | Production Replicability |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Container Runtime** | Docker Desktop for Mac (Apple Silicon) or Colima | Max 3.0 GB RAM limit in Docker settings, 2 vCPUs | Enable VirtioFS file sharing; allocate 3 GB memory limit in *Settings > Resources > Advanced* | Hosts isolated lab environments, runners, collectors, and emulated network containers | Prevents macOS memory pressure crashes and excessive swap memory churn | Standard development container engine used across modern enterprise NetDevOps |
| **Network Emulation Engine** | Linux Network Namespaces / containerlab / FRR | ~300–600 MB RAM for 2-tier Spine-Leaf topology | Use Alpine/Debian base containers running FRRouting; connect via Linux veth pairs | Provides isolated L3 BGP EVPN routing and interface QoS queuing controls | Eliminates requirement for heavy virtual machine hypervisors (e.g. CML / EVE-NG requiring 16+ GB) | Identical Linux routing and cgroups constructs used in production Kubernetes and edge nodes |
| **Traffic Generation & Packet Injection** | Scapy, iperf3, ping / hping3 inside containers | ~150–250 MB RAM per active traffic stream | Generate synthetic RoCEv2 (UDP 4791) bursts, DSCP-marked packets, and TCP microbursts | Injects synthetic test packets to trigger queue scheduling, ECN marking, and buffer occupancy | Prevents testbed resource exhaustion during high-volume packet injection experiments | Standard network validation and synthetic test automation methodology in enterprise QA |
| **Observability & Storage Layer** | Lightweight TSDB / Log storage (InfluxDB / Wazuh) | Max 1.5 GB RAM cap per running project | Configure short data retention policies (1–3 days) and minimal background compaction threads | Collects real-time queue metrics, syslog events, and synthetic probe latencies | Prevents uncontrolled time-series database disk and memory footprint growth | Directly mirrors cloud-native telemetry ingestion architectures (Prometheus/Grafana) |
| **Development & Workflow IDE** | VS Code (ARM64) + Terminal + Git | ~600–900 MB RAM host memory | Use remote container extension or local virtualenvs; disable heavy background indexing plugins | Authoring lab orchestration scripts, CI workflows, detection rules, and technical memos | Avoids IDE memory bloat leaving maximum headroom for container execution | Standard enterprise developer workstation configuration across top tech firms |
| **Lifecycle Management Policy** | One-Lab-at-a-Time Sequential Policy | Always guarantees 4.0–5.0 GB free host RAM | Standardized bash teardown script (`make clean` / `docker compose down -v`) after every lab milestone | Ensures crisp execution of every lab project without hardware throttling or system slowdown | Guarantees 100% reliable lab execution on standard consumer hardware (8 GB M1 MacBook Air) | Teaches disciplined DevOps hygiene and immutable infrastructure lifecycle patterns |
